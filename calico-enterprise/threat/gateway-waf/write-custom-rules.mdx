# Write custom rules with plugins

:::note

This feature is tech preview. Tech preview features may be subject to significant changes before they become GA.

:::

A `WAFPlugin` (namespace) or `GlobalWAFPlugin` (cluster) holds custom [ModSecurity SecLang](https://github.com/owasp-modsecurity/ModSecurity/wiki/Reference-Manual-(v3.x)) directives in four lifecycle slots — `config`, `before`, `rules`, `after` — for app-specific detections and false-positive exceptions the Core Rule Set doesn't cover on its own. Cluster operators wanting the same rules org-wide use `GlobalWAFPlugin` instead — same fields, different scope. For what each slot does and when it runs, see [Plugins — custom rules](./overview.mdx#plugins--custom-rules).

:::caution

`ctl:ruleEngine=Off` inside a chained rule or per-request disables the engine for that transaction only. A top-level `SecRuleEngine Off` is rejected by the admission webhook.

:::

:::note

`SecRuleRemoveById`/`ctl:ruleRemoveById` in `after` apply for the rest of phase processing — use to suppress your own false positives. Protected Core Rule Set baseline rules can't be removed from any slot; the webhook rejects the attempt.

:::

## Prerequisites

- Gateway WAF is enabled. See [Enable Gateway WAF](./enable.mdx).
- You have write access to `WAFPlugin` in your namespace (or `GlobalWAFPlugin` at cluster scope).
- A `WAFPolicy` or `GlobalWAFPolicy` exists to reference the plugin from — a plugin does nothing until a policy loads it. See [Attach WAF to a Gateway or route](./attach-waf-to-a-route.mdx).

## Write a plugin

1. Find your namespace's SecRule ID range. Every `SecRule`/`SecAction` needs an ID, and each namespace gets a 10,000-ID block enforced at admission:

   ```bash
   kubectl get namespace <your-namespace> \
     -o jsonpath='{.metadata.annotations.applicationlayer\.projectcalico\.org/waf-id-range}'
   # example output: 420000-429999
   ```

   The range is populated the first time a plugin is referenced in your namespace. See [SecRule ID ranges](./reference.mdx#secrule-id-ranges) for protected ranges and the allowlist.

1. Write the `WAFPlugin`, placing each rule in the slot that matches when it should fire. This example uses all four slots to protect a GraphQL API. The `4200xx` IDs below assume the `420000-429999` example range from the previous step — swap in IDs from your own namespace's range, or the admission webhook rejects the plugin with `IDOutsideRange`:

   ```yaml
   apiVersion: applicationlayer.projectcalico.org/v3
   kind: WAFPlugin
   metadata:
     name: graphql-waf
     namespace: platform
   spec:
     description: "GraphQL introspection guard and false-positive exceptions"

     config: |
       # Flag the application type so later rules can branch on it.
       SecAction \
         "id:420001,phase:1,pass,nolog,\
          setvar:tx.is_graphql=1"

     before: |
       # Allowlist the schema endpoint used by the internal schema registry —
       # skip WAF analysis entirely for that specific path.
       SecRule REQUEST_URI "@streq /graphql/schema-registry" \
         "id:420010,phase:1,pass,nolog,\
          ctl:ruleEngine=Off,\
          tag:allowlist"

     rules: |
       # Block introspection queries (production guard).
       SecRule TX:IS_GRAPHQL "@eq 1" \
         "id:420020,phase:2,deny,status:403,\
          msg:'GraphQL introspection blocked',\
          logdata:'body_snippet=%{MATCHED_VAR}',\
          chain"
       SecRule REQUEST_BODY "@rx __schema|__type" ""

       # Block suspicious user-agents known to scan GraphQL APIs.
       SecRule REQUEST_HEADERS:User-Agent "@pmf graphql-scanners.dat" \
         "id:420021,phase:1,deny,status:403,\
          msg:'Known GraphQL scanner blocked',\
          logdata:'ua=%{MATCHED_VAR}'"

     after: |
       # Remove a false positive: CRS rule 941130 fires on a legitimate
       # Content-Type value used by our GraphQL client library.
       SecRuleRemoveById 941130
   ```

   :::tip

   `@pmf` loads a data file, which must be bundled into the Coraza WASM filter image — ask your cluster operator, or use `@pm` (inline phrase match) for a short string list.

   :::

1. Reference the plugin from a `WAFPolicy`, in `spec.plugins[]` (load order = array position):

   ```yaml
   apiVersion: applicationlayer.projectcalico.org/v3
   kind: WAFPolicy
   metadata:
     name: platform-api-waf
     namespace: platform
   spec:
     targetRefs:
       - group: gateway.networking.k8s.io
         kind: HTTPRoute
         name: graphql-api
     action: Block
     plugins:
       - kind: WAFPlugin
         name: graphql-waf        # ← your plugin above
   ```

   If the policy also references a `GlobalWAFPlugin`, its slots load before the namespace plugin's slots at each position.

   :::note

   Not all SecLang directives are permitted — directives that read the filesystem, fetch remote rules, or write to arbitrary audit log paths are rejected. See [SecRule ID ranges](./reference.mdx#secrule-id-ranges) for the allowlist.

   :::

1. Confirm acceptance and reconciliation:

   ```bash
   kubectl get wafplugin graphql-waf -n platform -o yaml | grep -A10 "conditions:"
   kubectl get wafpolicy platform-api-waf -n platform -o yaml | grep -A20 "conditions:"
   ```

   `Ready=True` on the `WAFPolicy` confirms the merged ruleset passed validation and the `EnvoyExtensionPolicy` was programmed.

Gateway WAF runs the [OWASP Core Rule Set v4](https://coreruleset.org/docs/) via [Coraza](https://coraza.io/); the [ModSecurity reference manual](https://github.com/owasp-modsecurity/ModSecurity/wiki/Reference-Manual-(v3.x)) covers the full SecLang directive set.

## Example: unblock Kibana Discover

Kibana sends an Elasticsearch query in the body of its search requests, and a `url` argument on many requests. With the Core Rule Set enabled, the WAF reads the search body as an attack and the `url` argument as server-side request forgery, so Kibana Discover fails with HTTP 403. The Core Rule Set is working as designed — Kibana needs app-specific exceptions, the same way the Core Rule Set ships exceptions for applications such as phpMyAdmin and WordPress.

These exceptions change how the Core Rule Set runs, so they belong in a `GlobalWAFPlugin`. A namespaced `WAFPlugin` cannot alter a baseline rule — the admission webhook rejects it with `ProtectedIDRemoval` — and a namespaced `WAFPolicy` cannot reference a `GlobalWAFPlugin`. A cluster-scoped `GlobalWAFPlugin`, loaded through the `default` `GlobalWAFPolicy`, is the only configuration that both tunes the Core Rule Set and reaches the gateway.

A Discover search carries a full Elasticsearch query in its body — sort fields, highlight tags, field lists, nested filters, and large numbers. The Core Rule Set cannot tell this query apart from an attack: many of its rules each match some part of the body and add to an anomaly score, and rule `949110` blocks the request once that score crosses the threshold. The set of rules that match changes from query to query, because each search sends different fields and values. Removing one rule, or even the whole SQL-injection group, does not reliably unblock Discover — another rule brings the score back over the threshold on the next query.

So the exception skips Core Rule Set inspection of the request **body**, instead of removing named rules — and it matches as narrowly as it can: only a `POST`, to the Manager gateway host, on the exact search path. The WAF still inspects the URL, headers, and method on that request, still inspects the body on every other path, and the exception never applies on another gateway that serves the same path. The `url` argument is different: it rides in the URL, has a fixed name, and trips two specific rules, so its exception removes just that argument from those two rules — pinned to the same host.

| Request | What fires | Exception |
| :--- | :--- | :--- |
| `POST /tigera-kibana/internal/bsearch` on the Manager host (Discover search) | The search body scores across several Core Rule Set rules and crosses the anomaly threshold (`949110`) | Skip request-body inspection for that one request |
| `/tigera-kibana/...` requests with a `url` argument, on the Manager host | `931100`, `934110` read the `url` argument as server-side request forgery | Remove the `url` argument from those two rules |

Apply the plugin and reference it from the `default` `GlobalWAFPolicy`, which every `WAFPolicy` reads:

```yaml
apiVersion: applicationlayer.projectcalico.org/v3
kind: GlobalWAFPlugin
metadata:
  name: kibana-exceptions
spec:
  description: "Core Rule Set exceptions for Kibana on the Manager gateway"
  before: |
    # Discover sends its Elasticsearch query in the body of a POST to one search
    # path. The Core Rule Set scores that body as an attack, so skip request-body
    # inspection for exactly that request: on the Manager gateway host, a POST to
    # the exact search path. URL, header, and method inspection stay in force.
    # Replace manager.example.com with your Manager gateway hostname
    # (Manager spec.ingressGateway.hostname). SERVER_NAME is the gateway host from
    # the :authority header. The ctl sits on the last rule of the chain, not the
    # first, so it only runs when the whole chain matches. The chained rules carry
    # no id — the admission check rejects a chained rule that has one.
    SecRule SERVER_NAME "@streq manager.example.com" \
      "id:100000001,phase:1,pass,nolog,t:none,t:lowercase,chain"
      SecRule REQUEST_METHOD "@streq POST" \
        "t:none,chain"
      SecRule REQUEST_FILENAME "@streq /tigera-kibana/internal/bsearch" \
        "t:none,t:urlDecodeUni,t:normalizePath,ctl:requestBodyAccess=Off"
    # The url argument reads as server-side request forgery. On the Manager host
    # only, remove that one argument from the two forgery rules.
    SecRule SERVER_NAME "@streq manager.example.com" \
      "id:100000002,phase:1,pass,nolog,t:none,t:lowercase,chain"
      SecRule REQUEST_FILENAME "@beginsWith /tigera-kibana/" \
        "t:none,t:urlDecodeUni,t:normalizePath,\
         ctl:ruleRemoveTargetById=931100;ARGS:url,\
         ctl:ruleRemoveTargetById=934110;ARGS:url"
---
apiVersion: applicationlayer.projectcalico.org/v3
kind: GlobalWAFPolicy
metadata:
  name: default
spec:
  plugins:
    - kind: GlobalWAFPlugin
      name: kibana-exceptions
```

If the cluster already has a `default` `GlobalWAFPolicy`, do **not** re-apply the block above — a second `kubectl apply` drops any field the file omits, so a `defaultAction: Block` would fall back to `Detect` for every policy that inherits it. Append the plugin with a patch instead:

```bash
kubectl patch globalwafpolicy default --type=json \
  -p='[{"op":"add","path":"/spec/plugins/-","value":{"kind":"GlobalWAFPlugin","name":"kibana-exceptions"}}]'
```

Apply the full `GlobalWAFPolicy` block above only on a cluster that has no `default` yet.

:::caution

Trade-off: on the Manager gateway host, the WAF does not inspect the **body** of a Discover search (the `POST` to `/tigera-kibana/internal/bsearch`). Its URL, headers, and method are still inspected, and every other request, path, and host is inspected in full.

:::

:::note

The plugin **loads** on every WAF-covered gateway and route: the controller merges `GlobalWAFPolicy/default` into every `WAFPolicy` in the cluster. The `SERVER_NAME` host match and the path match keep it **firing** only for Kibana on the Manager gateway, so a second gateway serving the same paths is unaffected. Set the host in both rules to your Manager gateway hostname.

:::

:::note

There is no namespaced way to drop a single Core Rule Set rule — a `WAFPlugin` cannot remove or retarget a baseline rule (IDs `900000`–`999999` or the Tigera-managed range). The nearest namespaced alternative is a `WAFPolicy` with `action: Detect`, in the Manager gateway's namespace (`calico-system`, unless `Manager.spec.ingressGateway.gatewayNamespace` says otherwise), targeting the `calico-manager-route` `HTTPRoute`. The cost is that it turns the **whole** Manager gateway to Detect — it stops blocking for the entire Manager UI, not just Kibana — because the operator renders that route as one rule with no path match and reverts hand edits. Use the `GlobalWAFPlugin` above if you need to keep blocking everywhere else.

:::

:::note

The rule IDs `100000001` and `100000002` are safe to reuse and to copy for other apps: namespace ID windows stop at `99,999,999` and the protected ranges (Core Rule Set and Tigera baseline) stop at `1,099,999`, so IDs from `100,000,000` up can't clash with a tenant's rules or a baseline rule. The search endpoint can differ between Kibana versions — read the `tigera_secure_ee_waf` log index for your cluster to confirm the search path, and add a rule per search endpoint rather than loosening the exact-path match. Because the body exception keys on the request (`SERVER_NAME` + `POST` + path) and not on named rules, it keeps working as the Core Rule Set changes which rules match.

:::
