# Configure egress gateways, Azure user-defined routes

## Big picture

Control the source IP address seen by external services and appliances by routing the traffic from
certain pods through egress gateways. $[prodname] adds a user-defined route (UDR) for each egress
gateway address so that the Azure fabric can reach it, and updates the routes as gateway pods move.

:::note

Azure offers two ways to make egress gateway addresses reachable. This page covers user-defined
routes, which need no BGP session and no Azure Route Server. For the BGP approach, where gateways
use native VNet IPs advertised to an Azure Route Server, see
[Configure egress gateways, Azure](egress-gateway-azure.mdx).

:::

## Value

Controlling the source IP seen when traffic leaves the cluster allows groups of pods to be
identified by external firewalls, appliances, and services. Egress gateway addresses come from a
$[prodname] IP pool that is outside your VNet address space, so the Azure fabric has no route to
them and drops the traffic.

A UDR for each egress gateway address makes it reachable from elsewhere in Azure, from peered VNets,
and from on-premises networks. $[prodname] adds and removes these routes for you. When a gateway pod
is rescheduled to another node, $[prodname] updates the route to point at the new node, so you do not
maintain any routes yourself.

## Concepts

### Why Azure drops egress gateway traffic

Azure installs system routes only for the address prefixes declared on a VNet. An egress gateway
address is outside those prefixes, so Azure does not know where to send it. Return traffic fails,
and other Azure resources cannot reach the address.

### User-defined routes

A UDR makes an address prefix reachable at a specific VM. $[prodname] writes one route for each
egress gateway address. The route is a `/32`, and its next hop is the internal IP of the node that
currently hosts the gateway pod. Because a `/32` is more specific than Azure's system route for the
same range, Azure uses the UDR instead. The node must also have IP forwarding enabled on its NIC, so
that it accepts and forwards packets for an address that is not its own.

### Route tables and tags

$[prodname] writes route entries only. You create and maintain the route tables themselves, their
subnet associations, network security group rules, VNet peerings, and node IP forwarding.

Two kinds of tag control where routes are written:

| Tag | On | Means |
| --- | --- | --- |
| `calico-egw-management: true` | the route table, in Azure | $[prodname] can write and remove its own routes in this table |
| the tags listed in `spec.azure.routeTables.tags` | the `EgressGateway` resource | the routes for this gateway's addresses go in tables that have these tags |

$[prodname] writes only to a table that has both the management marker and a matching routing tag.
If a table has routing tags but no marker, $[prodname] leaves it alone and logs the reason. This
means that a route is never written to a table that $[prodname] is not allowed to clean up later.

If an `EgressGateway` has no `spec.azure` section, its addresses are not routed in Azure. If its
tags match no table, no routes are written.

### Which pods get a route

$[prodname] writes a route for each pod that carries the `operator.tigera.io/egress-gateway` label
and is in the same namespace as the `EgressGateway` that the label names. The Tigera operator sets
this label on every egress gateway pod that it creates. Host-networked pods are skipped, because
their address is the node's own.

$[prodname] does not check that the pod's address comes from the gateway's IP pools. Anyone who can
create or change pods in a namespace that has an `EgressGateway` can therefore make Azure route
traffic for a pod address of their choosing to the node that runs the pod.

An `EgressGateway` in any namespace can also select any table that has the management marker, by
naming that table's tags. Anyone who can create or change an `EgressGateway` can therefore have
routes written to any table that $[prodname] manages.

Allow only cluster administrators to create or change `EgressGateway` resources, and to create or
change pods in the namespaces that hold them.

## Before you begin

**Required**

- $[prodname] CNI and IPAM
- An egress gateway deployment, as described in
  [Configure egress gateways, on-premises](egress-gateway-on-prem.mdx)
- An Azure identity for $[prodname]: a workload identity (recommended, because it stores no secret
  in the cluster) or a service principal
- Permission in Azure to create a custom role, assign it to the identity, and tag route tables

**Not supported**

- Azure VNet CNI
- IPv6

$[prodname] CNI and IPAM are required. Controlling the egress gateway's IP is a feature of
$[prodname] IPAM. Azure VNet CNI assigns VNet addresses instead, so there is no address outside the
VNet to route.

### Set up the identity

$[prodname] uses one Azure identity for the whole cluster.

For a workload identity, enable the OIDC issuer and workload identity on the cluster. Then add a
federated credential to the identity for the cluster's issuer, with the subject
`system:serviceaccount:calico-system:calico-kube-controllers` and the audience
`api://AzureADTokenExchange`.

A service principal needs no setup here. You give its secret to the cluster when you
[create the AzureIdentity resource](#create-the-azureidentity-resource).

### Grant the identity access to your route tables

Create a custom role with only the actions needed to manage route entries:

```json
{
  "Name": "Calico egress gateway routes",
  "Actions": [
    "Microsoft.Network/routeTables/read",
    "Microsoft.Network/routeTables/routes/read",
    "Microsoft.Network/routeTables/routes/write",
    "Microsoft.Network/routeTables/routes/delete"
  ],
  "AssignableScopes": ["/subscriptions/<subscription-id>"]
}
```

The role does not include `Microsoft.Network/routeTables/write`, because $[prodname] writes route
entries and never creates, changes, or deletes a route table.

The role needs all four of its actions. Without `Microsoft.Network/routeTables/routes/read`,
$[prodname] cannot list the routes in a table, so it leaves that table alone: it writes no routes to
it, and it does not remove the routes of gateway pods that have gone.

Assign the role to the identity. You can assign it at any scope: a single route table, a resource
group, or the whole subscription. A broader assignment does not give $[prodname] more to change,
because it writes only to tables that have the `calico-egw-management` marker. Assigning the role on
each table is the most restrictive option, but then each table that you add later needs its own
assignment. Azure returns only the route tables that the identity can read, so if a table has no
role assignment, $[prodname] cannot see it, whatever tags it has.

:::note

Azure can take up to 10 minutes to apply a new role assignment. Until it does, $[prodname] cannot
see the table and does not write any routes. This looks the same as a missing role assignment. If
no routes appear once that time has passed, see
[Troubleshoot egress gateways](troubleshoot.mdx#routes-are-missing-or-traffic-is-dropped-user-defined-route-setups).

:::

### Create the AzureIdentity resource

Create an `AzureIdentity` resource. It is cluster-scoped, it must be named `default`, and each
cluster has one. The Tigera operator reads it and attaches the credential to the kube-controllers
pod, so you do not need to edit that pod or its service account.

For workload identity:

```bash
kubectl apply -f - <<EOF
apiVersion: operator.tigera.io/v1
kind: AzureIdentity
metadata:
  name: default
spec:
  type: WorkloadIdentity
  subscriptionID: <subscription-id>
  workloadIdentity:
    clientID: <client-id>
EOF
```

For a service principal, create the secret first, in the `tigera-operator` namespace and with the
client secret under the key `clientSecret`:

```bash
kubectl create secret generic azure-service-principal \
  --namespace tigera-operator \
  --from-literal=clientSecret='<client-secret>'
```

```bash
kubectl apply -f - <<EOF
apiVersion: operator.tigera.io/v1
kind: AzureIdentity
metadata:
  name: default
spec:
  type: ServicePrincipal
  subscriptionID: <subscription-id>
  servicePrincipal:
    clientID: <client-id>
    tenantID: <tenant-id>
    clientSecret:
      name: azure-service-principal
EOF
```

Where:

- `subscriptionID` is required for both types. It tells $[prodname] which subscription to work in,
  and only route tables in that subscription are read. It is not used to authenticate.
- `type` selects which block to use. You must include the block that matches `type`, and you cannot
  include the other one.
- To rotate a service principal credential, update the secret. The operator then restarts
  kube-controllers so that it picks up the new value.
- A change to the `AzureIdentity` restarts kube-controllers in the same way.

### Prepare the Azure network

For each consumer subnet or VNet, you need to set up four things:

**A route table, associated with the consumer subnet.** Associate the table with the subnet that the
traffic comes *from*, not with the subnet that your gateway nodes are in. The gateway node is the
virtual appliance for the route, and Azure warns that applying a route table to an appliance's own
subnet can send traffic back to it. Tag the table with the management marker, `calico-egw-management`
set to `true`, so that $[prodname] can manage it. Any other value counts as no marker. Then add a
routing tag for the gateways that use the table, such as `calico-egw` set to `blue`. This command
adds both tags and keeps the table's other tags:

```bash
ROUTE_TABLE_ID=$(az network route-table show --resource-group <resource-group> \
  --name <route-table> --query id --output tsv)
az tag update --resource-id "$ROUTE_TABLE_ID" --operation Merge \
  --tags calico-egw-management=true calico-egw=blue
```

**NIC IP forwarding**, on every node that can host an egress gateway. Without it, the node drops
packets for the egress gateway address instead of forwarding them. Run egress gateways on a
dedicated node pool so that only those nodes need it. On AKS, enable IP forwarding in the node
pool's virtual machine scale set, which is in the cluster's node resource group, and apply the
change to the nodes that already exist as well as to new ones.

**Network security group rules** that allow the traffic that the egress gateways send:

| Network security group for | Direction | Source | Destination |
| --- | --- | --- | --- |
| Your gateway nodes | Outbound | The egress pool CIDR | `VirtualNetwork` |
| The consumer subnet or VM | Inbound | The egress pool CIDR | `VirtualNetwork` |

Network security groups are stateful, so they allow the replies without rules of their own. Add
rules for the opposite direction only if something must open connections to an egress gateway
address.

Azure's default rules allow traffic between addresses in the `VirtualNetwork` service tag, and
Azure works out that tag separately for each network interface, from the routes that apply to it.
The subnet that your gateway nodes are in has no route for the egress pool, so the pool is not in
the gateway nodes' tag, and without the outbound rule their network security group drops the traffic
that the gateways send. A consumer subnet's tag can include the egress addresses, through the UDRs
in its route table, but the inbound rule allows the traffic without depending on that.

Azure evaluates a network security group on a subnet and one on a network interface, and both must
allow the traffic. On AKS, the cluster's network security group is in the node resource group. If
your gateway nodes are in a subnet that you created, check any network security group on that
subnet as well.

**VNet peering** between any consumer VNet and the cluster VNet, so that the next-hop node address
resolves. Use global peering if the VNets are in different regions. The peering from the consumer
VNet to the cluster VNet must allow forwarded traffic. Traffic from an egress gateway has a source
address outside the cluster VNet, so Azure treats it as forwarded, and drops it as it enters the
consumer VNet unless that peering allows it. The peering from the cluster VNet to the consumer VNet
does not need this setting.

### Provision an egress IP pool

Create a small pool that holds the source addresses you want this application to use:

```bash
kubectl apply -f - <<EOF
apiVersion: projectcalico.org/v3
kind: IPPool
metadata:
  name: egress-ip-blue-pool
spec:
  cidr: 100.64.0.144/28
  blockSize: 32
  nodeSelector: "!all()"
  vxlanMode: Always
  natOutgoing: false
EOF
```

Where:

- `natOutgoing` must be `false`. If it is `true`, the node masquerades the traffic to its own
  address, and the destination never sees the egress gateway address.
- The pool CIDR is outside your VNet address space. This is why the UDR is needed.
- `blockSize: 32` puts a single address in each block, so a gateway scheduled to one node does not
  claim addresses that other nodes could use.

### Deploy egress gateways with Azure routing

Add a `spec.azure` section to the `EgressGateway` naming the tags of the route tables its addresses
belong in. To add it to a gateway that already exists, patch the gateway rather than applying a new
manifest, so that its other settings, including its pod labels, stay as they are:

```bash
kubectl patch egressgateway <name> -n <namespace> --type merge \
  -p '{"spec": {"azure": {"routeTables": {"tags": [{"key": "calico-egw", "value": "blue"}]}}}}'
```

For a new gateway, create a namespace for it, and then the gateway:

```bash
kubectl create namespace calico-egress
```

```bash
kubectl apply -f - <<EOF
apiVersion: operator.tigera.io/v1
kind: EgressGateway
metadata:
  name: egress-gateway-blue
  namespace: calico-egress
spec:
  replicas: 2
  ipPools:
    - name: egress-ip-blue-pool
  azure:
    routeTables:
      tags:
        - key: calico-egw
          value: blue
  template:
    metadata:
      labels:
        egress-code: blue
EOF
```

Where:

- A table is selected if it has **any one** of the listed tags. Each tag needs both a `key` and a
  `value`, so a general key such as `env` cannot select tables that you did not intend.
- Several gateways can write to one table, and one gateway can write to several tables. A table
  selected by more than one gateway holds the routes for all of them.
- $[prodname] routes the address of each pod that this `EgressGateway` runs. The addresses come from
  the IP pools named in `spec.ipPools`.

Run the gateways in a namespace that only cluster administrators can create or change pods in, and
allow only cluster administrators to create or change `EgressGateway` resources, as described in
[Which pods get a route](#which-pods-get-a-route).

Then annotate the namespaces or pods that should use the gateway, exactly as for any other egress
gateway deployment. The gateway in this example runs in the `calico-egress` namespace, so clients in
other namespaces need a namespace selector as well as a selector. For example, for a namespace:

```bash
kubectl annotate ns <namespace> \
  egress.projectcalico.org/selector="egress-code == 'blue'" \
  egress.projectcalico.org/namespaceSelector="kubernetes.io/metadata.name == 'calico-egress'"
```

For pods, and for other ways to select gateways, see
[Configure namespaces and pods to use egress gateways](egress-gateway-azure.mdx#configure-namespaces-and-pods-to-use-egress-gateways).

### Verify the routes

Check that the gateway pods are running, and that each route table that the gateway selects has a
route for each of their addresses. To list the $[prodname] routes in a table:

```bash
az network route-table route list \
  --resource-group <resource-group> \
  --route-table-name <route-table> \
  --query "[?starts_with(name, 'calico-egw-')]" \
  --output table
```

$[prodname] names its routes `calico-egw-<cluster>-<address>`, where `<address>` is the egress
gateway address with `.` replaced by `-`. The `<cluster>` part identifies the cluster that owns the
route, which matters when two clusters share a route table. It is the first 16 hexadecimal
characters of the SHA-256 hash of the cluster's GUID. To get your cluster's identifier:

```bash
kubectl get clusterinformation default -o jsonpath='{.spec.clusterGUID}' | sha256sum | cut -c1-16
```

On macOS, use `shasum -a 256` in place of `sha256sum`.

The kube-controllers log also shows the full prefix, in the `ourRoutes` field of the line it logs
each time it reads your route tables.

Then test the data path from a consumer **outside** the cluster, such as a VM in a peered VNet.
Testing from a cluster node does not work, because the node reaches the egress gateway address over
the cluster overlay and never uses the UDR.

:::note

The controller re-reads your route tables every five minutes, so a newly tagged table can take up to
five minutes to receive routes. If routes are still missing after that, see
[Troubleshoot egress gateways](troubleshoot.mdx#routes-are-missing-or-traffic-is-dropped-user-defined-route-setups).

:::

### Remove Azure routing

To stop routing a gateway's addresses, remove the `spec.azure` section from its `EgressGateway`, or
delete the `EgressGateway`. $[prodname] then removes that gateway's routes from every table that it
manages. Check that the route tables no longer hold routes for the gateway's addresses.

If a route is still there, look for the error in the kube-controllers log. $[prodname] tries again at
every sync, so once you fix the cause, the route is removed within five minutes. A fix to the
identity's role can take up to 10 minutes longer, while Azure applies it.

Leave the management marker, the role assignment, and the `AzureIdentity` in place until you have
confirmed that the routes are gone. If you remove any of them first, $[prodname] can no longer manage
the table, so any routes left in it stay there, and you have to delete them yourself.

### Remove leftover routes

While a table has the management marker and the identity can read it, $[prodname] removes any route
of its own that no gateway needs at every sync, including routes left over from an earlier failure.
Routes are left behind when $[prodname] can no longer manage them or remove them, for example when
the marker is removed from the table, when the identity loses access to it, or when the
`AzureIdentity` or the cluster is deleted. A cluster also never removes another cluster's routes,
even from a table that both share.

To remove them, look in each table for routes whose names begin with the cluster's prefix, which is
`calico-egw-` followed by the cluster's identifier and a `-`, as described in
[Verify the routes](#verify-the-routes). Delete each one that no running gateway uses.

You cannot work out a cluster's identifier once the cluster is deleted, so record it for each cluster
that shares a table.

## Limitations

- **$[prodname] CNI is required.** Azure VNet CNI does not use $[prodname] IPAM, so there is no
  address outside the VNet to route.
- **One route table per subnet.** Azure allows only one route table per subnet, so $[prodname]
  routes share the consumer subnet's existing table. That table holds up to 400 routes, which you
  can raise to 1,000 with Azure Virtual Network Manager. If two clusters serve the same subnet, they
  share the table. Each cluster manages only its own routes, but the limit applies to both.
- **Each gateway pod takes a route in every table that its gateway selects.** A rolling update
  briefly needs routes for both the old and the new pods. When a table is full, Azure rejects new
  routes. To stay under the limit, give consumers of different gateways their own subnets and tables.
- **Route names that begin with `calico-egw-` are reserved.** $[prodname] overwrites or removes any
  route whose name begins with its own cluster's prefix, and leaves other routes alone.
- **Internet-bound traffic does not keep the egress gateway address.** The AKS outbound load
  balancer masquerades it. The address is useful for destinations in Azure, in peered VNets, and
  on-premises.
- **One identity and one subscription.** Route tables in another subscription are not read, even if
  the identity can reach them.
- **Azure permission problems show only in the kube-controllers log.** `tigerastatus` does not
  report them. See
  [Troubleshoot egress gateways](troubleshoot.mdx#routes-are-missing-or-traffic-is-dropped-user-defined-route-setups).
- **IPv4 only.**
- **The egress gateway address is not fixed to a pod.** An IP pool usually holds more addresses than
  there are gateway pods, so a rescheduled gateway usually gets a different address. Allowlist the
  pool CIDR rather than individual addresses.
- **A route can keep pointing at a node that has stopped.** $[prodname] removes a gateway pod's
  route when Kubernetes deletes the pod, not when its node stops or becomes unreachable. A pod on an
  unreachable node stays in `Terminating` until the node is deleted or you force-delete the pod, so
  its route stays until then.
- **$[prodname] writes routes one at a time**, so a large rollout takes longer as the number of
  gateways and route tables increases.
- **You must keep NIC IP forwarding enabled.** An AKS node image upgrade can turn it off, so
  re-apply it after upgrading, as described in [Prepare the Azure network](#prepare-the-azure-network).
