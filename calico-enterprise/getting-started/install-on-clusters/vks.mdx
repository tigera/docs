# vSphere Kubernetes Service (VKS)

## Big picture

Install $[prodname] as a Supervisor Service on vSphere Kubernetes Service (VKS), and deploy it to guest clusters.

## Before you begin

This guide requires:

- **VM Images**: Ubuntu or Photon OVA images registered for a supported TKR version, with TKR in a healthy state. For Windows node pools, Windows Server OVA images are also required.
- **vSphere Resources**: Sufficient capacity to provision guest clusters with at minimum:
    - 1 control plane node
    - 3 Linux worker nodes
- **OCI Registry**: An OCI-compliant registry configured in vSphere for storing package manifests and container images.
- **Tigera registry credentials** for accessing the Tigera container registry (contact the Tigera team).
- VKS v3.8 and above
- vCenter v9.1.1 and above

### Networking

| Configuration | Dataplane | Encapsulation | BGP |
|---|---|---|---|
| Linux only (default) | IPTables | IPIP | Enabled |

## How to

Setting up $[prodname] on VKS has two main phases: set it as a Supervisor Service (Part 1) in vSphere Client (one time), then deploy it to a guest cluster (Part 2). For Air-gapped environments follow the additional steps in the Air-gapped environment section.

### Part 1: Set up the Supervisor Service (one time cluster admin setup)

1. In the vSphere Client - Container Registries page setup the Tigera container registry's credentials for pulling Calico Enterprise images from Tigera's private container registry.
      -  Use `quay.io` as the Registry host URL, and Username/Password provided by Tigera.
    For air-gapped installs, add the private registry that holds the $[prodname] images instead (see [Copy the images to the private registry](#copy-the-images-to-the-private-registry)).

2. In the vSphere Client - Supervisor Management page:
   - Create a new Supervisor Service (or add a new version to an existing one).
   - Upload Supervisor service Package and PackageMetadata resources (example below) and complete the setup workflow.
   - Register the Supervisor Service and set `registryName` to match the registry name configured for Tigera's private container registry.
     For air-gapped installs, also add `chartRepository` to the service YAML configuration, and set it to the private registry path that holds the $[prodname] Helm chart (see [Copy the add-on to the private registry](#copy-the-add-on-to-the-private-registry)):

     ```yaml
     chartRepository: oci://<private-registry>/<path>
     ```

```yaml
---
apiVersion: data.packaging.carvel.dev/v1alpha1
kind: Package
metadata:
  name: calico-enterprise-svs.tigera.io.$[releaseVersion]
spec:
  refName: calico-enterprise-svs.tigera.io
  version: $[releaseVersion]
  template:
    spec:
      fetch:
      - imgpkgBundle:
          image: quay.io/tigera/calico-enterprise-svs:$[releaseTitle]   #Change this to the registry where the carvel package is getting picked up
      template:
      - ytt:
          paths:
          - service
          - kapp
      - kbld:
          paths:
          - "-"
          - .imgpkg/images.yml
          - kbld/
      deploy:
      - kapp: {}
---
apiVersion: data.packaging.carvel.dev/v1alpha1
kind: PackageMetadata
metadata:
  name: calico-enterprise-svs.tigera.io
spec:
  displayName: "Calico Enterprise SVS"
  shortDescription: "Manages Calico Enterprise Addon Repository and Installation"
```

### Part 2: Deploy a guest cluster with Calico Enterprise

#### Guest cluster prerequisites

- **Tigera license file** (contact the Tigera team).
- **Dynamic PV provisioning** via a StorageClass, required for Elasticsearch storage.

#### Step 1 (optional): Apply the AddonConfig

An AddonConfig is needed only if you want to change the default $[prodname] configuration, for example to create a cluster with Windows nodes. It is not required for a Linux-only cluster that uses the defaults.

The following example AddonConfig enables the Windows dataplane and disables policy recommendation.

:::info

Update the following fields before applying:
- `metadata.name` and `metadata.namespace`
- `spec.values.helmValues.installation.registry` to use $[prodname] images from a private registry (for air-gapped installs). This should be the same registry where $[prodname] images are pushed to using [Copy the images to the private registry](#copy-the-images-to-the-private-registry). Optionally `spec.values.helmValues.installation.imagePath` can be set if the $[prodname] images were pushed to a specific folder within the private registry.

:::

:::note

All $[prodname] features (`logCollector`, `logStorage`, `manager`, `monitor`, `policyRecommendation`) are optional. Only `apiServer` is required. Set any unwanted features to `false`.

:::

```bash
kubectl apply -f ./addon-config.yaml
```

```yaml
apiVersion: addons.kubernetes.vmware.com/v1alpha1
kind: AddonConfig
metadata:
  name: <cluster-name>-calico-enterprise   # The AddonConfig name has to be in this format eg. cluster1-calico-enterprise
  namespace: <cluster-namespace>
spec:
  values:
    helmValues:
      # Every option from tigera-helm-charts/tigera-operator/values.yaml may be
      # set here. Anything not specified falls back to the default declared in
      # the AddonConfigDefinition schema. The fields below are illustrative;
      installation:
        calicoWindowsDataplane:
          enabled: true
      policyRecommendation:
        enabled: false
```

:::note

The Addon framework expects the `AddonConfig` name to use the format `<cluster-name>-<addon-name>`. If the name does not match this format, the framework ignores the `AddonConfig` and creates a new one with default values instead.

:::

#### Step 2 (optional): Apply the Custom AddonInstall resource

A custom AddonInstall resource is needed only if you want to control which clusters get upgraded. It lets you upgrade clusters selectively. Use `spec.clusters.selector.matchLabels` to specify the labels that a cluster must have, and then add those labels to the Cluster resources you want to upgrade.

```bash
kubectl apply -f ./addon-install.yaml
```

```yaml
apiVersion: addons.kubernetes.vmware.com/v1alpha1
kind: AddonInstall 
metadata: 
  labels:
    addon.kubernetes.vmware.com/addon-name: calico-enterprise 
    addon.kubernetes.vmware.com/addon-namespace: vmware-system-vks-public
    addons.kubernetes.vmware.com/category: cni
  name: <addon-install-name>
  namespace: <cluster-namespace>
spec: 
  addonRef:
    name: calico-enterprise
    namespace: vmware-system-vks-public 
  clusters:
  - selector: 
      matchLabels:
        <AddonInstallLabelKey>: <AddonInstallLabelValue>      # Eg. cluster-group: calico-group-1
    constraints:
      expression: cluster.cniRefName() = "calico-enterprise" && cluster.kubeProxyConfiguration().enabled == true
  releaseFilter:
    ref:
      name: calico-enterprise.tigera.io.$[releaseVersion]
  stopMatchingBehavior: Retain
```

#### Step 3: Apply the Cluster Resource

The following example creates a cluster with Linux and Windows node pools. To create a Linux-only cluster, remove the Windows node pool (`windows-pool`).

Update the following fields before applying:
- `metadata.name` and `metadata.namespace`
- `spec.topology.variables[].value.cniRef` (name and namespace of the $[prodname] addon)
- If you applied a custom AddonInstall in Step 2, add its label (`<AddonInstallLabelKey>: <AddonInstallLabelValue>`) to `metadata.labels`.
- Node pool configuration (VM class, storage class, replicas) as needed for your environment

```bash
kubectl apply -f ./cluster.yaml
```

```yaml
apiVersion: cluster.x-k8s.io/v1beta2
kind: Cluster
metadata:
  name: <cluster-name>
  namespace: <cluster-namespace>
spec:
  clusterNetwork:
    pods: {cidrBlocks: [100.96.0.0/11]}
    services: {cidrBlocks: [100.64.0.0/13]} # required for Windows (becomes serviceCIDRs)
    serviceDomain: cluster.local
  topology:
    classRef: {name: builtin-generic-v<classRefVersion>, namespace: vmware-system-vks-public}
    version: <vkr-k8s-version>
    controlPlane:
      replicas: 1
      metadata: &ubuntu
        annotations: {run.tanzu.vmware.com/resolve-os-image: "os-name=ubuntu,os-version=24.04"}
    workers:
      machineDeployments:
      - {class: node-pool, name: linux-pool-1, replicas: 3, metadata: *ubuntu,
          variables: {overrides: [{name: vmClass, value: best-effort-large}]}}
      - {class: node-pool, name: linux-pool-2, replicas: 2, metadata: *ubuntu}
      - class: node-pool
        name: windows-pool
        replicas: 2
        metadata:
          annotations: {run.tanzu.vmware.com/resolve-os-image: "os-name=windows,os-version=2022"}
        variables: {overrides: [{name: vmClass, value: best-effort-xlarge}]}
    variables:
    - {name: bootstrapAddons, value: {cniRef: {name: calico-enterprise, namespace: vmware-system-vks-public}}}
    - {name: vmClass, value: best-effort-xlarge}
    - {name: storageClass,  value: vsan-esa-default-policy-raid5}
    - {name: vsphereOptions, value: {persistentVolumes: {defaultStorageClass: vsan-esa-default-policy-raid5}}}
    - {name: kubernetes, value: {certificateRotation: {enabled: true, renewalDaysBeforeExpiry: 90}}}
    # Must be cluster-level: the Calico ACD only reads spec.topology.variables.
    - {name: osConfiguration, value: {windowsToolsConfig: {excludeNICs: ["cali*"]}}}
    - name: node
      value:
        firewall:
          inboundRules:
          - {protocol: tcp, fromPort: 179, toPort: 179}       # BGP
          - {protocol: udp, fromPort: 4789, toPort: 4789}     # VXLAN
          - {protocol: tcp, fromPort: 5473, toPort: 5473}     # Typha
          - {protocol: udp, fromPort: 51820, toPort: 51820}   # WireGuard
          - {protocol: tcp, fromPort: 8444, toPort: 8444}     # Linseed
          - {protocol: tcp, fromPort: 9090, toPort: 9090}     # Prometheus
          - {protocol: tcp, fromPort: 9200, toPort: 9200}     # Elasticsearch
          - {protocol: tcp, fromPort: 9300, toPort: 9300}     # Elasticsearch transport
          - {protocol: tcp, fromPort: 9443, toPort: 9443}     # Manager UI
```

#### Step 4: Retrieve the Guest Cluster Kubeconfig

Can be copied from the Supervisor.

#### Step 5: Wait for Core Components

Monitor the Tigera status until `calico` and `apiserver` report as `Available`:

```bash
kubectl get tigerastatus
```

At this point, all nodes should be in `Ready` state.

#### Step 6 (Windows only): Configure Windows nodes

Skip this step for Linux-only clusters.

1. After `apiserver` reports as `Available`, set `strictAffinity` to `true` in the IPAM configuration:

   ```bash
   kubectl patch ipamconfigurations default --type merge -p '{"spec":{"strictAffinity":true}}'
   ```

   If the IPAM configuration does not exist yet, create it:

   ```bash
   kubectl apply -f - <<EOF
   apiVersion: projectcalico.org/v3
   kind: IPAMConfiguration
   metadata: {name: default}
   spec: {strictAffinity: true}
   EOF
   ```

1. Install kube-proxy for Windows:

   ```bash
   curl -L https://raw.githubusercontent.com/kubernetes-sigs/sig-windows-tools/master/hostprocess/calico/kube-proxy/kube-proxy.yml | sed "s/KUBE_PROXY_VERSION/<YOUR_KUBERNETES_VERSION>/g" | kubectl apply -f -
   ```

   Replace `<YOUR_KUBERNETES_VERSION>` with the Kubernetes version of the guest cluster, for example `v1.36.4`.

   > 💡 **Tip:** The K8s version can be retrieved with `kubectl version -o json | jq -r '.serverVersion.gitVersion'`

   > ℹ️ **Note:** If the version returned is of the form `v1.36.4+vmware.2`, strip the `+vmware.2` suffix unless a VMware-provided kube-proxy image exists in the `sigwindowstools/kube-proxy` repository.
   > ℹ️ **Note:** For Air-gapped environments copy the kube-proxy.yaml to the air-gapped environment and make the changes.

#### Step 7: Apply the Tigera License

```bash
kubectl apply -f tigera-license.yaml
```

#### Step 8: Verify the Installation

Wait for all remaining components to become available:

```bash
kubectl get tigerastatus
kubectl get pods -A | grep -E 'tigera|calico'
```

Once all items in `tigerastatus` show `Available`, the installation is complete. You can now deploy workloads to validate networking.

### Air-gapped environments

An air-gapped environment has no or very limited internet access.
Clusters in such an environment can't pull the $[prodname] add-on or the $[prodname] images directly from Tigera's registries.
Instead, you copy these artifacts from Tigera's registries to a private registry that the environment can reach.

This involves two tasks:

1. [Copy the add-on to the private registry](#copy-the-add-on-to-the-private-registry), so that the Supervisor can install the $[prodname] Supervisor Service.
1. [Copy the images to the private registry](#copy-the-images-to-the-private-registry), so that guest clusters can run $[prodname].

#### Air-gapped prerequisites

- `imgpkg`, `helm`, and `yq` installed locally.
- Network access to both Tigera's registry and the private registry.
  If no single host can reach both, you can copy the artifacts through a tarball instead.
- Credentials to push to the private registry.
  `imgpkg` uses your local Docker configuration, or prompts you for credentials.

#### Copy the add-on to the private registry

The $[prodname] add-on consists of a Helm chart and a Supervisor Service (SVS) bundle.
Copy both to the private registry, then point the Supervisor Service at them.

##### Step 1: Copy the Helm chart

On a host that can reach `quay.io`, pull the $[prodname] add-on Helm chart and push it to the private registry:

```bash
helm pull oci://quay.io/tigera/calico-enterprise --version $[releaseVersion]
helm push calico-enterprise-$[releaseVersion].tgz oci://<private-registry>/<path>
```

Replace `<private-registry>/<path>` with the registry and path that will hold the chart.
Don't include the chart name (`calico-enterprise`) in the path.
You use the same value for `chartRepository` when you register the Supervisor Service in [Step 5](#step-5-upload-the-package-to-the-supervisor).

##### Step 2: Copy the SVS bundle to a tarball

On a host that can reach `quay.io`, copy the SVS bundle to a tarball:

```bash
imgpkg copy --bundle quay.io/tigera/calico-enterprise-svs:$[releaseTitle] --to-tar calico-enterprise-svs.tar
```

##### Step 3: Push the SVS bundle to the private registry

On a host that can reach the private registry, push the tarball:

```bash
imgpkg copy --tar calico-enterprise-svs.tar --to-repo <private-registry>/calico-enterprise-svs
```

:::caution

Use `imgpkg` to copy the bundle.
Don't copy individual images with `docker pull` and `docker push`.
Re-tagging images can change their manifest digests, and the bundle's `images.yml` lock file isn't updated to match.
kapp-controller then fails to fetch the images, with a `manifest unknown` error.

:::

:::tip

If one host can reach both registries, you can copy the bundle directly to the private registry and skip Step 3.
Replace `--to-tar calico-enterprise-svs.tar` with `--to-repo <private-registry>/calico-enterprise-svs`.

:::

##### Step 4: Update the package to use the private registry

The `Package` resource in `calico-enterprise-svs.yaml` is the only registry reference outside the bundles.
Update it to point to the SVS bundle in the private registry:

```bash
yq eval '
  (select(.kind == "Package") | .spec.template.spec.fetch[0].imgpkgBundle.image)
    = "<private-registry>/calico-enterprise-svs:$[releaseTitle]"
' -i calico-enterprise-svs.yaml
```

:::tip

To make the reference immutable, pin it to a digest.
The last line of the `imgpkg copy --to-repo` output shows the digest of the copied bundle.
In the `yq` command, replace `:$[releaseTitle]` with `@sha256:<digest>`.

:::

##### Step 5: Upload the package to the Supervisor

Upload the updated `Package` and `PackageMetadata` resources from `calico-enterprise-svs.yaml` on the vSphere Client Supervisor Management page, as described in [Part 1](#part-1-set-up-the-supervisor-service-one-time-cluster-admin-setup).
When you register the Supervisor Service, set `chartRepository` in the service YAML configuration to the Helm chart path from [Step 1](#step-1-copy-the-helm-chart). 
Also, set `registryName` that refers to the private registry registered with vSphere as a Container registry. 

:::caution

You can set `chartRepository` only once for each version of the Supervisor Service.
It is immutable and can't be updated later.

:::

#### Copy the images to the private registry

Before you create guest clusters, copy the $[prodname] images to the private registry, and configure the cluster to pull them from there.

1. Copy the $[prodname] images from `quay.io/tigera` to the private registry.
   Follow the steps in [Push $[prodname] images to your private registry](./private-registry/private-registry-regular.mdx#push-calico-enterprise-images-to-your-private-registry).

   :::caution

   Don't push $[prodname] images to a public registry.

   :::

2. If the private registry requires authentication, register it on the vSphere Client Container Registries page with its credentials. And use this name while setting up Supervisor service in the YAML service config as `registryName`

   ```yaml
   registryName: <registered-private-registry>
   ```

1. Add the private registry to the `installation` section of the AddonConfig.
   For more about the AddonConfig, see [Step 1 (optional): Apply the AddonConfig](#step-1-optional-apply-the-addonconfig).

   ```yaml
   apiVersion: addons.kubernetes.vmware.com/v1alpha1
   kind: AddonConfig
   metadata:
     name: <cluster-name>-calico-enterprise
     namespace: <cluster-namespace>
   spec:
     values:
       helmValues:
         installation:
           registry: registry.example.internal:5000/   # mirror host[:port]
           imagePath: tigera                            # optional; defaults to "tigera"
           # imagePrefix: ""                            # optional; only if your mirror renames images
   ```
