  A resource reference page describes one projectcalico.org API resource: what it represents, its fields, their types, accepted values, and defaults.
  Readers come to it while writing or reviewing a manifest.
  They look up one field and leave, so the page has to be complete, accurate, and easy to scan.

  A resource reference page only describes.
  It doesn't tell the reader how to set the resource up, and it doesn't explain why the feature exists.
  Link to how-to guides and explanation pages instead.

  Every resource page has the same sections, in the same order, with the same table columns.
  A script checks the pages against the CRD, so keep the table shape exactly as shown here.

  For other kinds of reference page, such as configuration options or what a feature supports, use reference.mdx.
  Don't hand-write a page for an API that is generated from source, such as the operator API.

  EXCEPTIONS

  These pages keep the structure but can't follow every rule. Follow the rules they can, and leave the rest as it is.
  - A spec that is generated from source, such as FelixConfiguration: a component renders the Spec section from JSON, in groups, with its own columns. Don't hand-write that Spec, and don't reshape it. Everything else on the page follows the template.
  - A resource that wraps a Kubernetes type, such as StagedKubernetesNetworkPolicy: list the fields the resource adds, and link to the Kubernetes API reference for the fields and nested types it inherits, instead of writing a section for each one.
  - A nested type that comes from a shared include, such as Rule or EntityRule: the include owns the heading and the anchor, because other pages and products link to it. Don't rename a shared heading on one page; change the include, and check every page that imports it, in every product.
  - The overview and index pages in reference/resources/ describe the resource set, not one resource. They don't use this template.

  Good examples in our docs:
  - calico/reference/resources/ipreservation.mdx, a small resource
  - calico/reference/resources/ippool.mdx, a resource with behavior sections
  - calico/reference/resources/bgppeer.mdx, a resource with nested types

## Definition

{/*
  REQUIRED: Definition

  Always use the heading "Definition".
  Under it, put Metadata, then Spec, then one section for each nested type, then Status.

  Every field table has these columns, in this order:

  | Field | Description | Accepted Values | Schema | Default |

  Keep all five columns on every table, and leave a cell empty rather than drop a column.
  Keep the same column order on nested type tables too.

  Field: the field name exactly as it appears in the manifest, and nothing else.
    If the field was added in a version readers may not have, append the version: `fieldName _(since v3.21.0)_`.
    If the field is deprecated, append `_(deprecated)_` and say in the description what to use instead.
  Description: what the field does, in a sentence or two.
    If the field is required, end with "Required."
    If it's required only in some cases, say when: "Required when `mode` is `Manual`."
    If it can't be combined with another field, say so: "Can't be set with `vxlanMode`."
    Put limits and validation rules here, or in Accepted Values when they're a range.
  Accepted Values: the values or ranges the API accepts, such as `Always`, `CrossSubnet`, `Never` or `20` to `32`.
    Leave it empty when any value of the schema type is accepted.
  Schema: the type: string, integer, boolean, float, list of strings, map of string to string, or a link to a nested type: [BGPPassword](#bgppassword), list of [Rule](#rule), [selector](#selector).
  Default: the value the API uses when the field is omitted, in code format.
    Leave it empty when there is no default.
*/}
